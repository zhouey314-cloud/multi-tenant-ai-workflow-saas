# 本地 API：事务与错误契约

这个工程用一条总部 → 门店 → 审核 → 发布链路，展示服务端租户过滤、资料继承、审核状态与审计记录。使用已公开的虚构用户和密码，适合复现流程与集成测试；身份切换是演示控制。

Node 24：`npm start`。默认只绑定 `127.0.0.1:8788`；支持 `PORT=0` 自动选端口和 `DEMO_DB=/private/path/snapshot.json`。启动输出实际监听地址。单个服务进程拥有一个 JSON 存储路径；多进程共享写入尚未支持。

请求头使用 README 中的 `x-demo-user` / `x-demo-password`。静态网站仍使用相同 core，原 URL 不变。

| 路径 | 行为 |
|---|---|
| GET /api/overview | 当前演示用户可见的资料、任务和审计 |
| POST /api/knowledge | id/title/body/visibility，租户与组织由服务端写入 |
| POST /api/tasks | id/title/knowledgeIds；引用必须属于当前可见集合 |
| POST /api/tasks/:id | `{ "to": "review" }` 等合法角色状态迁移 |

请求体上限 100000 bytes；拒绝数组/null、未知字段、畸形 JSON、无效 ID/标题和缺失的资料列表。任何请求都带 X-Request-Id；JSON 错误包含同一 request_id。401 为演示登录失败，403 为权限/状态拒绝，404 为路径不存在，413 为体积超限，422 为输入无效，500 为内部或持久化失败。500 不返回内部文件路径或异常文本。

## 写盘失败时到底发生什么

每次变更先克隆当前状态，执行策略后将候选 JSON 写入唯一 0600 临时文件、fsync 并 rename。只有持久化成功才发布内存状态。因此写盘失败时任务和审计都不会出现在后续查询里；原实现直接修改内存再 save，失败请求会遗留“幽灵任务”。现有文件若损坏，启动失败并保留文件，不自动覆盖为 seed。
